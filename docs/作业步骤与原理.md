# 电控第一次作业 · 每一步在干什么、为什么这么做

> 这份文档的目的：**让你知道自己在做什么，而不是照抄命令。**
> 阅读方式：做到哪一步就看哪一节。每节四块 —— **做什么 / 为什么 / 搞错了会怎样 / 能带走的思想**。

---

## 0. 先说全局：这份作业到底在训练什么

三道题看起来是"点灯、定时器、看门狗"，本质上是**一个最小可用的嵌入式固件工程闭环**：

```
时钟（心脏） → GPIO（手脚） → 定时器中断（心跳节拍） → 看门狗（纪律检查） → 调试器观察（眼睛）
```

把这五件事走通，你就拥有了做任何电机控制项目的地基。
而**电机调试考核**要用的恰好就是这五件事（1 kHz 中断、看门狗保护、Ozone 看变量）——所以这份作业不是"额外的活"，是**热身**。

---

## 1. 工具链全景：每个软件扮演什么角色

| 工具 | 角色 | 类比 |
|---|---|---|
| **STM32CubeMX** | 图形化配置芯片、生成初始化代码骨架 | 画 CAD 图纸 + 备料 |
| **CMake** | 读 `CMakeLists.txt`，算出"编译哪些文件、用什么参数" | 写菜谱 |
| **Ninja** | 按 CMake 算好的菜谱，真正驱动编译器 | 厨师长（调度） |
| **arm-none-eabi-gcc** | 把 C/C++ 编译成 STM32 能执行的机器码 | 厨师（真正动手） |
| **VS Code** | 编辑代码 + 一键触发上面三个 | 工作台 |
| **Ozone / 调试器** | 把芯片里的变量"实时"显示出来 | 示波器 / 监护仪 |

**关键理解**：这六个东西是**流水线**，任何一环出问题，症状都长得像"编译不过"。所以我们要**一步一步验证**，而不是一口气跑完再猜哪里坏了。

## 2. 逐步拆解

### S1 · 选芯片（型号必须和丝印一致）

- **做什么**：CubeMX 里选 `STM32F103C8Tx`。
- **为什么**：生成的启动文件、链接脚本、寄存器定义、Flash/RAM 大小**全都依赖具体型号**。
- **搞错了会怎样**：程序能编译，但烧进去就跑飞/不跑 —— 这是最难查的一类问题（因为"看起来一切正常"）。
- **带走的思想**：**嵌入式开发里，"硬件事实"永远优先于"文档/记忆"**。丝印、手册、时钟树显示的数值，才是真相。

### S2 · RCC 配外部晶振（HSE = Crystal）

- **做什么**：告诉芯片"PD0/PD1 上接了一颗 8 MHz 晶振"。
- **为什么**：芯片内部有一个 RC 振荡器（HSI，约 8 MHz），但**精度差、随温度漂移**；外部晶振精度高得多。而**时间**是你这份作业的全部：1 ms 必须真的是 1 ms。
- **搞错了会怎样**：时钟树拉不到 72 MHz（只能到 64 或 48），或者能配到 72 但实际频率偏差大（tick 涨得比 1000/s 快或慢）。
- **带走的思想**：**控制系统的第一个精度来源是时基**。电机控制里"1 kHz 控制周期"如果不准，PID 的 D 项（对时间最敏感）就全错。

### S3 · SYS 选 Serial Wire（★最关键的一步）

- **做什么**：把 PA13/PA14 保留给 SWD 调试接口。
- **为什么**：这两个引脚**默认就是调试口**，但 CubeMX 生成代码时会把它们初始化成**普通 GPIO**——一旦烧进去，调试器就再也连不上了（因为"用来调试的那两根线"被程序自己占用了）。
- **搞错了会怎样**：下载一次之后，调试器报"无法连接"，以为板子坏了。
- **救命办法**：让调试器"连接时复位 + 全片擦除"再下载一次。
- **带走的思想**：**外设复用是双刃剑**。一个引脚能被配置成多种功能，代价是"一旦配错就可能把自己锁在门外"。工程上这类问题叫"自锁风险"，对策是**默认保留调试通道**。

### S4 · PC13 配推挽输出、初始电平 Low

- **做什么**：把 PC13 配成推挽输出、初始低电平、无上下拉、低速。
- **为什么**：
  - **推挽（Push-Pull）**：能主动输出高和低两种电平（开漏只能拉低或高阻，需要外部上拉）。驱动 LED 用推挽最直接。
  - **低电平点亮**：蓝板的板载 LED 是"阳极接 3.3 V → 电阻 → LED → PC13"，所以 PC13 输出低时形成回路，灯亮。**灯亮与否取决于电路接法，不取决于你写 0 还是 1。**
  - **速度选 Low**：PC13 属于**备份域引脚**，驱动能力很弱（手册约 3 mA），并且不支持高速翻转，选 Low 更稳。
- **搞错了会怎样**：写成高电平 → 灯不亮（你会以为程序没跑）；速度选 High → 可能干扰或驱动不足。
- **带走的思想**：**GPIO 配置的每一项都在回答一个物理问题**：驱动什么？电流多大？多快？——而不是"随便选个默认值"。

### S5 · TIM2 配成 1 ms 更新中断

**做什么**：TIM2 时钟源用内部时钟，PSC = 71，ARR = 999，打开 TIM2 全局中断。

**为什么**：这两个数是"从 72 MHz 变出 1 ms"的唯一办法。

```
定时器时钟 = 72 MHz
PSC = 71  →  计数时钟 = 72 MHz ÷ (71+1) = 1 MHz   （每 1 µs 数一次）
ARR = 999 →  数 1000 次溢出一次 = 1000 µs = 1 ms   ✅
```

**为什么定时器时钟是 72 MHz 而不是 APB1 的 36 MHz**（这条规则很多人栽）：

```
APB1 总线时钟 = 36 MHz（因为 APB1 分频 = ÷2）
但规则规定：定时器挂在 APB1 上、且 APB1 分频 ≠ 1 时，定时器时钟 = APB1 × 2 = 72 MHz
（这就是作业要求你写清楚的"定时器时钟从哪来"）
```

**为什么不能用 `HAL_Delay` 或空循环加 tick**：
- `HAL_Delay` 是**阻塞式**的——CPU 干等着，什么都做不了；
- 空循环的耗时取决于编译优化等级，**换个优化等级就不准了**。

而定时器中断是**硬件保证的节拍**：CPU 该干嘛干嘛，时间一到自动打断它去执行回调。

- **搞错了会怎样**：PSC/ARR 算错 → tick 涨得不是 1000/s（截图就露馅）；用 `HAL_Delay` → 整个程序被卡死在一个循环里。
- **带走的思想**：**实时系统的节拍必须由硬件产生，不能由软件"数"出来。**（电机控制里的控制周期同理。）

### S6 · IWDG 启用（分频 64、Reload 1249 ≈ 2 s）

- **做什么**：启用独立看门狗，超时约 2 秒。
- **为什么**：看门狗是一个**独立于 CPU 的倒计时炸弹**。程序一旦卡死（死循环、指针跑飞），没人去喂它，它就会**强制复位芯片**——这是系统唯一的"自救"手段。
- **超时怎么算**：

```
超时 = (Reload + 1) × 分频 ÷ LSI = (1249 + 1) × 64 ÷ 40000 = 2.000 s
（F103 的 LSI 约 40 kHz；LSI 是芯片内部低速振荡器，精度不高，所以只能说"约 2 秒"）
```

- **为什么超时要远大于 1 ms**：如果超时只有 1 ms，tick 还没来得及加 1 就被复位了，你根本看不到它增长。**超时必须明显大于"喂狗周期"**。
- **为什么关不掉**：这是**安全设计**。如果软件能关掉看门狗，那它出 bug 时也能"顺手"把自己保护关掉 —— 看门狗就白设了。一旦启动，只能靠复位停止。
- **搞错了会怎样**：第 1 题还没喂狗 → 芯片**每 2 秒复位一次**（这正是题目预期现象）；用调试器暂停超过 2 秒 → 调试器掉线（因为 CPU 停了，看门狗还在跑）。
- **带走的思想**：**看门狗保护的是"程序卡死"，不是"程序算错"。** 这一点在考核里会更深入——那时候要判断"什么时候**不该**喂狗"。

### S7 · 时钟树把 HCLK 拉到 72 MHz

- **做什么**：在 `Clock Configuration` 里输入 72，让 CubeMX 自动解出 PLL 配置（HSE 8 MHz × 9 = 72 MHz）。
- **为什么**：F103 最高主频 72 MHz，跑满能获得最强的算力；同时要**确保 APB1 = 36 MHz**（外设总线有速度上限）。
- **搞错了会怎样**：拉不到 72（HSE 没配）或超频（芯片不稳定、发热、随机死机）。
- **带走的思想**：**时钟树是"预算分配"**：总频率有限，怎么分给 CPU、总线、外设，是一个权衡。

### S8 · Project Manager：CMake + Generate Under Root + Keep User Code

- **做什么**：选工具链 CMake、生成位置在工程根、保留用户代码。
- **为什么**：
  - **CMake 工具链**：让工程能被 VS Code + CMake Tools + Ninja 构建（队里的标准工作流）。
  - **Keep User Code**：CubeMX 只能在 `/* USER CODE BEGIN */ ... /* USER CODE END */` 这些"圈起来的地盘"之间保留你的代码。**圈外的代码每次重新生成都会被覆盖。**
- **搞错了会怎样**：代码写错地方 → 下次 CubeMX 一生成，你的代码全没了。
- **带走的思想**：**代码生成器与手写代码必须有明确的边界。** 这条边界在作业里体现为：**所有业务代码只写 `Tasks/` 和 `USER CODE` 区块**。

### S9 · 换成老师发的 `CMakeLists.txt` 模板

- **做什么**：删掉 CubeMX 生成的 `CMakeLists.txt`，用老师模板替换。
- **为什么**：CubeMX 默认那份只做到"能编"；老师的模板额外做了几件事：
  1. **自动把 `Tasks/` 目录纳入编译**（`set(user_folders "Tasks")`）—— 你不用每次手动往构建脚本里加文件；
  2. 打开 **C++20**（考核里我们用 C++ 写分层模块）；
  3. 统一警告与优化配置；
  4. 编译后**自动生成 `.hex` / `.bin`**（有些烧录工具只认这两种格式）。
- **搞错了会怎样**：`Tasks/` 里的代码"写了但没编进去" → 报"未定义引用"，或者改了代码没反应。
- **带走的思想**：**约定优于配置**。团队统一模板的意义是"你只需要知道把代码放哪，剩下交给模板"。

### S10 · 先建 `Tasks/inc`、`Tasks/src`，**再** Configure

- **做什么**：建目录 → 然后才执行 CMake 配置。
- **为什么**：模板里这一行是关键：

```cmake
file(GLOB_RECURSE ${user_folder}_srcs "${user_folder}/*.*")
```

`GLOB` 是**在 Configure 那一刻扫描目录，把文件清单固化下来**。目录不存在 → 扫到空清单 → 你的代码**永远不进编译**。

- **搞错了会怎样**：目录后建 → 即使有代码也不编译；而且**以后补建目录也不会自动生效**，必须重新 Configure。
- **带走的思想**：**构建系统对目录结构拍的是"快照"。** 凡是"改了目录/新增了文件夹"，第一反应就是**重新 Configure**。（考核项目里同理。）

### S11 · Configure 与 Build 是两件事

| 阶段 | 做什么 | 类比 |
|---|---|---|
| **Configure** | 读 `CMakeLists.txt`，找编译器、算参数、生成 `build/Debug/` 里的构建脚本 | 写菜谱 |
| **Build** | 按构建脚本真正编译、链接，产出 `.elf` | 炒菜 |

- **toolchain 文件**（`cmake/gcc-arm-none-eabi.cmake`）回答的是："用哪个编译器？什么 CPU？链接脚本在哪？"——比如 `-mcpu=cortex-m3`、`-T STM32F103xx_FLASH.ld`。
- **CMakePresets** 把参数组合固化：`Debug` 用 `-O0 -g3`（好调试），`Release` 用 `-Os -g0`（省空间）。
- **为什么要先编"空壳"**：此时 `Tasks/` 是空的，编出来的东西不含你的代码。但这证明了 **工具链 + 模板是通的**。之后再出问题，就一定是**你的代码**的问题，而不是环境的锅。
- **带走的思想**：**隔离故障**。一次只让一个变量变化，问题才好定位。

### S12 · 业务代码只写 `Tasks/`；`main.c` 里只调初始化，`while(1)` 保持空

- **为什么**：
  1. **重新生成不丢**：`Tasks/` 是模板纳入的目录，CubeMX 不会碰它；
  2. **可移植**：把"业务逻辑"和"芯片相关代码"分开，换芯片时业务逻辑能复用（考核项目里我们就是这么做的：算法层完全不依赖 HAL，所以能在电脑上跑测试）；
  3. **`while(1)` 为什么是空的**：所有工作都在**中断**里做。这叫**事件驱动**——主循环空转，硬件节拍一到就打断执行。
- **搞错了会怎样**：把业务代码塞进 `main.c` 的 `while(1)` → 下次生成被覆盖；或和中断抢时间导致节拍抖动。
- **带走的思想**：**分层与解耦**。

### S13 · `volatile uint32_t tick`（为什么必须加 `volatile`）

- **做什么**：把 tick 定义成**全局 + volatile** 的 `uint32_t`。
- **为什么**：编译器优化时会假设"变量只被当前代码改"，于是可能把 tick **缓存进寄存器**，主循环里读到的永远是旧值；而**中断里改的值主循环看不到**。`volatile` 就是告诉编译器："这个变量随时可能被别处（中断/硬件）改，每次都必须从内存真读。"
- **搞错了会怎样**：Ozone 里看 tick 一直是 0 或不动；程序逻辑也错（读不到最新值）。
- **带走的思想**：**中断与主流程共享的变量，有三条铁律**：① 加 `volatile`；② 注意读写的原子性（32 位以下通常一次读完，64 位/结构体不行）；③ 复杂数据要用临界区保护（关中断/加锁）。

### S14 · 回调只写一份；用 C++ 写要加 `extern "C"`

- **做什么**：`HAL_TIM_PeriodElapsedCallback` 全工程**只写一份**，放在 `Tasks/` 里；用 C++ 编译时函数前加 `extern "C"`。
- **为什么**：
  - HAL 库里这个回调是 **`__weak`（弱符号）**：HAL 给了一个空实现，**你写一个同名函数就会覆盖它**。这是"钩子（hook）"设计。
  - 但如果**两处**都有定义（比如 CubeMX 也在 `main.c` 生成了），链接器就报**重复定义** —— 所以作业特意提醒你：多出来那份要删掉。
  - **`extern "C"`**：C++ 为了支持函数重载，会把函数名"改名"（name mangling，比如 `_Z24HAL_TIM_...`）。而 HAL 是 C 写的、按原始名字找符号 → 不加 `extern "C"` 就**链接不上**。
- **带走的思想**：**C 与 C++ 混编的边界必须显式声明**；库提供的"弱符号钩子"是嵌入式最常见的扩展点。

### S15 · 还要自己调用 `HAL_TIM_Base_Start_IT(&htim2)`

- **为什么**：CubeMX 的 `MX_TIM2_Init()` **只配置、不启动**（我们已核实全工程没有 `Start_IT`）。生成器不知道你什么时候想开始计时，所以把"启动"这步留给你。
- **搞错了会怎样**：**tick 永远是 0**，回调永远不触发（这是最典型的"看起来都配对了但就是不动"）。
- **带走的思想**：**init（配置）与 start（启动）分离**，是嵌入式驱动的通用设计（CAN、UART、ADC 都一样）。

### S16 · 第 2 题的证据：Ozone 里看 tick "每秒 +1000"

- **为什么必须"程序运行中"看**：CPU 一停下来（断点/暂停），**时间就停了**，而看门狗还在跑 → 2 秒后复位、调试器掉线。**实时系统的量测不能用"停表"方式。**
- **为什么"单看一个静止的数值不算完成"**：一个静止的 500 证明不了"它在以 1000/s 增长"。**证据必须是时间序列**（Timeline / 连续监视）。
- **带走的思想**：**做实验要留下能反驳自己的数据。** 这条在考核答辩里就是加分点。

### S17 · 第 3 题的证据：去掉喂狗，看 tick 涨到约 2000 再归零

- **为什么是约 2000**：2 s ÷ 1 ms = 2000 拍。
- **为什么会"归零"**：复位后，**启动代码会把全局变量区（.bss/.data）初始化**——`tick = 0` 就是被这段启动代码清掉的。**复位 ≠ 断电**，但复位后 C 语言层面的全局变量会被重新初始化。
- **为什么这一题的对照价值最大**：同一份代码，只去掉一行 `HAL_IWDG_Refresh`，现象从"tick 一直涨"变成"涨到 2000 归零循环" —— 这直接**证明了看门狗真的在工作**。
- **带走的思想**：**一次只改一个变量（对照实验）**。所以作业要求第 2、3 题"分两次下载、分两次截图"。

### S18 · 为什么截图/照片必须放附录，且要三类证据

| 证据 | 证明什么 |
|---|---|
| 灯亮**照片** | 硬件真的动了（不是仿真、不是"我改了代码"） |
| tick 曲线（**每秒 +1000**） | 定时中断真的在按 1 ms 跑 |
| tick 涨到 2000 **归零** | 看门狗真的在复位芯片（保护生效） |

- **带走的思想**：**"做了"和"能证明做了"是两件事。** 工程交付看的是证据链。

### S19 · GitHub 公开仓库 + 邮件交付

- **为什么**：可复现（别人拿到能自己编译）、可审计（有提交历史）、可溯源（链接写进邮件正文）。
- **为什么代码要放在 `Tasks/` 里并且能一条命令编出来**：因为老师会**真的去编**。
- **带走的思想**：**交付物 = 代码 + 说明 + 证据 + 复现步骤**，缺一不可。

## 4. "搞错了会怎样"总表（排错用）

| 症状 | 最可能的原因 | 先查哪里 |
|---|---|---|
| 下载一次后**再也连不上** | SYS 没选 Serial Wire，PA13/14 被占 | 用"连接时复位 + 全片擦除"救回，然后回 CubeMX 补上 |
| 灯**不亮** | 电平写反了 / 引脚配错 | 确认 LED = PC13、初始电平 Low、推挽 |
| tick **一直是 0** | 没调 `HAL_TIM_Base_Start_IT` | 在 `Tasks` 初始化里加上 |
| tick **涨得不对**（不是 1000/s） | PSC/ARR 或定时器时钟算错 | 回时钟树看 `APB1 Timer clocks` |
| 链接报 `multiple definition` | 回调写了两份 | 全工程搜 `HAL_TIM_PeriodElapsedCallback`，只留 `Tasks` 里的 |
| 链接报 `undefined reference`（C++ 写的回调） | 忘了 `extern "C"` | 给回调加 `extern "C"` |
| 改了 `Tasks` 里的代码**没反应** | `Tasks` 目录没进编译（Configure 时目录还不存在） | 确认目录存在后**重新 Configure** |
| CubeMX 重新生成后**代码没了** | 代码写在 `USER CODE` 区块之外 | 业务代码一律放 `Tasks/` |
| 调试器**2 秒后掉线** | 看门狗复位（CPU 停着也在倒计时） | 让程序运行，别长时间停在断点 |
